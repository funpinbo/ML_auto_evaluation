# 03. 아키텍처 철학

> **작성자: 사용자.** "무엇을 만들까"가 아니라 **"결정이 갈릴 때 무엇을 우선하는가"** 를 적는 문서입니다.
> architecture-analyst Agent 는 후보 아키텍처를 이 우선순위로 채점합니다. `{{ }}` = 필수.

> 아래는 01 (로컬·1인·"하루" 목표, 성능/보안 요구 없음)을 근거로 잡은 **경량 기본값**입니다.
> 틀렸거나 다른 걸 쓰고 싶으면 직접 바꾸세요.

## 1. 핵심 원칙 (우선순위 순)
<!-- 3~7개. 위에 있을수록 충돌 시 이긴다. -->
1. 단순함 우선 — "하루" 안에 동작하는 MVP, 과설계·조기 분산 금지
2. 로컬 단일 프로세스 — 분산/클라우드 불필요 (01 NFR-002·004 와 일치)
3. 결과 비교 용이성 > 성능 (01 KPI-02, NFR-001)

## 2. 품질 속성 우선순위
<!-- 1(가장 중요) ~ 7 순위를 매기세요. 동순위 금지. -->
| 품질 속성 | 순위 | 비고 |
|-----------|------|------|
| 개발 속도 (Time to market) | 1 | "하루" 목표 (01 §0) |
| 유지보수성 | 2 | 1인 유지보수 |
| 가용성/신뢰성 | 3 | 로컬 실행, 다운되면 재시작으로 충분 |
| 확장성 | 4 | 동시 사용자 1명 전제 (NFR-004) |
| 성능 (Latency/Throughput) | 5 | 목표 없음 (NFR-001) |
| 운영 비용 | 6 | 로컬 실행이라 거의 무관 |
| 보안 | 7 | 외부 노출 없음 전제 (NFR-003) |

## 3. 아키텍처 스타일 선호
- **기본 형태:** 단일 프로세스 모놀리스 (FastAPI 한 프로세스, 분리 불필요)
- **통신 방식:** 동기 REST 만 (비동기 이벤트/메시징 불필요)
- **상태 관리:** 평가 결과는 로컬 파일/SQLite 에 저장, 서비스 로직 자체는 stateless

## 4. 기술 선호 & 금지
| 구분 | 기술 | 이유 |
|------|------|------|
| 선호 | SQLite | 별도 DB 서버 없이 로컬 파일 하나로 평가 결과 저장 — 1인 로컬 도구에 가장 단순 |
| 허용 | 필요한 Python 라이브러리 전반 | 1일 프로젝트, 특별한 제약 없음 |
| 금지 | 클라우드 매니지드 서비스, 별도 메시지 브로커/분산 시스템 | "로컬 단일 프로세스" 원칙(1번)과 상충 |

## 5. 데이터 철학
- **일관성 모델:** 강한 일관성 불필요 (단일 사용자, 동시 접근 없음 — NFR-004)
- **데이터 소유권:** 단일 프로세스가 전체 데이터 소유, 모듈 분리 불필요
- **보존/삭제 정책:** 평가 결과는 사용자가 직접 지우기 전까지 로컬에 보존

## 6. 인프라 & 배포
- **실행 환경:** 로컬 PC (별도 서버/클라우드 불필요, 07 기술 제약과 일치)
- **환경 구성:** 단일 환경 (로컬 개발=운영, dev/staging/prod 구분 불필요)
- **IaC:** 불필요
- **배포 전략:** 불필요 (로컬 실행, `python run.py` 류의 실행 스크립트로 충분)

## 7. 관측성 (Observability)
- **필수 신호:** 콘솔 로그만 (개인 도구, 메트릭/트레이스 불필요)
- **알림 기준:** 불필요 (on-call 없음)

## 8. 보안 원칙
- 로컬 전용 — 외부 네트워크에 노출하지 않는 것이 핵심 원칙. 그 외 인증/암호화는 불필요 (01 NFR-003)

## 9. 결정 기록 (ADR) 정책
- **ADR 필수 대상:** N/A (1일 프로젝트 — 중요한 선택은 이 문서나 00 해석서에 바로 기록)
- **저장 위치:** 기본값 유지 (`workspace/project/adr/ADR-xxx.md`), 필요 시에만 사용

## 10. 피하고 싶은 안티패턴
- 과설계 — 조기 마이크로서비스화, 불필요한 분산/클라우드 의존
- 불필요한 인증·배포 파이프라인 구축 (1일 목표와 상충)
