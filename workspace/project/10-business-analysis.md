# 10. 비즈니스 모델 분석

>

## 5. 기능 우선순위 (가치 × 노력)
| FR | 비즈니스 가치 (1-5) | 구현 노력 (1-5) | 리스크 | 권장 Phase | 근거 |
|----|---------------------|-----------------|--------|-----------|------|
| FR-001 | 5 | 2 | 낮음 | P1 | 다대다 연결이 없으면 "복수 모델/데이터 비교"라는 핵심 가치 제안 자체가 성립하지 않음(01§1). SQLite 기반 N:M 매핑 테이블 CRUD로 구현 노력은 낮음(04 Run/Evaluation 엔티티 설계와 직결, PK/FK 확정됨). |
| FR-002 | 5 | 3 | 중간 | P1 | 업로드가 없으면 파이프라인이 시작되지 않는 진입점이며, Jupyter 대체라는 동기(01§1)의 1차 관문. 노력이 FR-001보다 높은 이유는 PyTorch/scikit-learn 두 형식을 다뤄야 하고, 모델 호출 인터페이스(함수 시그니처) 세부가 00§3.1#2 에서 10/20 단계로 위임되어 구현 중 설계가 추가로 필요하기 때문. |
| FR-003 | 3 | 2 | 낮음(단, 00§3.2#10 지표-문제유형 불일치 처리 미정) | P1 | 지표 선택은 가치 있지만, "선택"이라는 UI 자체는 단순 드롭다운+sklearn 지표 함수 호출 수준으로 노력이 낮음. 다만 FR-004 실행의 입력 파라미터이므로 최소 기능(지표 선택 가능)은 P1에 포함하되, 분류/회귀 호환성 검증 같은 고도화는 범위 축소 1순위 후보(Q9 완화 방침). |
| FR-004 | 5 | 3 | 중간 | P1 | "Run 1클릭 자동 평가"가 Jupyter 수동 평가 대비 핵심 차별점이자 01§1 문제 정의의 직접 해결책. 노력이 중간인 이유는 N:M 조합 × 선택 지표를 순회하며 모델 로드·predict·채점·Run/Evaluation 저장까지 두 프레임워크 분기 처리가 필요하기 때문. |
| FR-005 | 4 | 2 | 낮음 | P1(단순 비교표/기본 그래프) → P2(상관관계 등 고도화) | 결과를 "숫자보다 그래프로" 보는 것이 Jupyter 대비 2차 차별점(01§5 FR-005 동기)이지만, 최소 비교(표 또는 단일 막대그래프)만으로도 "한눈에 비교"라는 Job은 일부 충족 가능. pandas 기반 지표 비교 그래프는 노력이 낮아 P1에 포함하되, 지표 간 상관관계 그래프는 Q9 일정 리스크 발생 시 가장 먼저 줄일 수 있는 범위로 P2 권장. |

## 6. MVP 정의
- **포함 FR (사용자가 정의한 "하루" 목표 MVP, 01§9 마일스톤과 일치):** FR-001, FR-002, FR-003, FR-004, FR-005 전체. 사용자 본인이 01§5 에서 5개 FR 모두를 Must 로 지정했고, 00§6 GO 판정에서도 확신도 L 인 Must FR 이 없다고 확인되었으므로 범위를 임의로 줄이지 않는다.
- **일정 리스크 대응 축소판(Fallback, Q9 완화 방침 — "안 되면 범위를 더 줄인다"):** 핵심 파이프라인 FR-001 + FR-002 + FR-004(업로드 → 연결 → Run 자동 평가, 지표는 고정 기본값 1종으로 임시 처리, 결과는 raw 표로만 노출)만으로도 "동작하는 최소 파이프라인"으로 인정하고, 시간이 허락하면 FR-003(지표 선택 UI)과 FR-005(그래프 시각화)를 순서대로 추가한다. 이 경우에도 01§5 의 FR 자체(Must 지정)는 변경하지 않으며, `/aidlc-plan` 단계에서 Task 순서/산출물 수준(완성도)만 조정한다.
- **MVP 성공 판단 기준:** Given 2개 이상의 모델과 1개 이상의 데이터셋이 업로드된 상태, When 사용자가 UI 에서 N:M 조합을 만들고 지표를 선택해 Run 을 클릭하면, Then Run 레코드 1건과 그에 속한 Evaluation 레코드들이 저장되고(KPI-02: 완료 모델 수 = 입력 모델 수), 결과 화면에서 모델별 지표 비교 그래프가 렌더링된다(FR-001~005 가 끝에서 끝까지 끊김 없이 동작).
