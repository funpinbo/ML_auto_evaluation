# FR-004. 평가 자동 실행 (Run)

## 사용자 스토리
사용자로서 모델과 데이터를 연결한 뒤 Run 버튼만 누르면 자동으로 평가가 실행되길 원한다, 왜냐하면 평가 과정을 직접 코드로 돌릴 필요 없이 한 번에 처리하고 싶기 때문이다. (01§5 원문)

## 전제
- FR-001 로 Link(모델-데이터 조합) 1건 이상 존재
- FR-003 으로 각 조합에 대해 지표 1개 이상 선택됨

## 화면 흐름 (10§4 사용자 여정 4단계)
1. 연결/지표 선택 화면에 "Run" 버튼이 있다. 버튼은 Link 가 1건 이상이고 지표가 선택된 상태에서 활성화된다.
2. 사용자가 Run 버튼을 클릭하면, 선택된 모든 Link × 선택 지표 조합이 하나의 Run 으로 묶여 서버에 제출된다.
3. 서버는 동기(블로킹) 로 조합을 순차 평가(QS-1 — 명시적 지연 목표 없음, 02§3.2 Q9 리스크 참고)하고, 완료되면 Run 결과 화면(FR-005)으로 이동하거나 결과 링크를 보여준다.
4. 평가 도중 콘솔에 INFO(Run 시작/완료)/WARN(skipped_incompatible, P2)/ERROR(status=error) 로그가 남는다(user/02§7).

## API 계약 참조 (20§5)
- `POST /runs` {combinations: [{model_id, dataset_id, metrics:[...]}]} → 201 {run_id, evaluations:[{model_id, dataset_id, metric, status, value}]}

## 수용 기준 (Given/When/Then)

### AC-1 (기본 흐름 — 01§5 원문 수용 기준, MVP 성공 판단 기준의 핵심)
Given UI 에서 연결된 Model-Dataset 조합 2개 이상과 각각에 선택된 지표,
When 사용자가 Run 버튼을 클릭,
Then 시스템이 그 조합들을 하나의 Run(run_id 1건)으로 묶어 자동으로 평가하고, 조합×지표 개수만큼의 Evaluation 레코드가 저장된다.

### AC-2 (Run 1건 = 여러 조합을 아우름)
Given Link 3건(각기 다른 (model, dataset) 쌍), 각 Link 에 지표 1개씩 선택,
When 사용자가 Run 버튼을 한 번 클릭,
Then Run 레코드는 1건만 생성되고, 그 Run 에 속한 Evaluation 레코드가 3건(조합당 1건) 생성된다. 각 Evaluation 은 run_id 로 동일 Run 에 귀속된다.

### AC-3 (평가 성공 — 호환 조합)
Given problem_type="classification" Model 과 그에 호환되는 지표(Accuracy) 선택,
When Run 실행,
Then 해당 Evaluation 은 `status=success`, `value` 에 숫자형 지표값이 저장된다. 콘솔에 INFO 로그(Run 완료)가 남는다.

### AC-4 (평가 실패 — 계산 중 예외, P1 pass-through)
Given predict 호출 또는 지표 계산 중 예외가 발생할 조합(예: FR-003 AC-4 의 비호환 지표 pass-through 상황),
When Run 실행,
Then 해당 Evaluation 은 `status=error`, `value=NULL` 로 저장되고, 나머지 조합의 평가는 중단되지 않고 계속 진행된다(Run 전체가 하나의 예외로 실패하지 않음 — QS-7 "Run 전체는 에러 없이 완료").

### AC-5 (Run 응답으로 결과 즉시 확인 가능)
Given Run 요청이 완료된 상태,
When 클라이언트가 `POST /runs` 응답을 받으면,
Then 응답에 run_id 와 evaluations 배열(model_id, dataset_id, metric, status, value)이 포함되어 있어, 별도 조회 없이도 바로 결과를 알 수 있다.

### AC-6 (재시작 후 데이터 보존 — QS-2)
Given 이전에 수행한 Run 과 Evaluation 레코드가 SQLite 에 저장되어 있는 상태,
When 서버 프로세스를 재시작(`python run.py`)한 뒤,
Then 기존 Run/Evaluation 레코드가 그대로 조회된다(GET API 로 확인).

## KPI-02 해석 (analytics 팀 부재 — product 가 직접 작성, D-04 근거)
- **산식:** KPI-02 = (Run 내 `status='success'` Evaluation 이 1개 이상 있는 Model 수) / (해당 Run 에 입력된 전체 Model 수)
- **집계 규칙(D-04):** `skipped_incompatible` 또는 `error` 만 있는 Model 은 분자에서 제외하되, 분모(입력 모델 수)에는 포함한다. Evaluation 레코드 자체는 삭제/누락시키지 않는다(패턴 — LTM §2).
- **검증 방법(수동/qa 자동화 대상):** Run 완료 후 `GET /runs/{id}/results` 또는 DB 조회로 Evaluation.status 분포를 집계해 success 모델 수 / 입력 모델 수를 계산한다.
- **MVP 성공 판단 기준(10§6)과의 연결:** "Given 모델 2개 이상 업로드 ... Then Run 1건 + Evaluation 레코드들 저장(KPI-02=완료 모델 수/입력 모델 수)"의 핵심 산출물이 본 FR 의 AC-1/AC-2 다.

## Out of scope (본 스토리에서 하지 않음)
- 비동기/백그라운드 Run 처리(progress bar, 작업 큐) — 20§2 에서 Celery/Redis 등 비동기 큐는 03§4 금지 기술로 실격. 동기 블로킹 처리가 확정 아키텍처(D-01)
- Run 취소/재시도 UI — 01§5·10§6 수용 기준에 없음, 범위 추가하지 않음(모호하면 질문으로 남긴다는 원칙에 따라 Task 후보로도 올리지 않음 — 필요성 자체가 식별되지 않음)
