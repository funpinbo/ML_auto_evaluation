- API 계약(20-architecture-analysis.md§5): `POST /links {model_id, dataset_id} → 201` / `GET /links` → 목록. `model_dataset_link` 테이블은 복합 PK(model_id, dataset_id) 뿐이고 별도 link_id 없음(app/eval/repository.py L57-61) — 응답 바디는 `{model_id, dataset_id}` 형태가 자연스러움(models/datasets 의 `{model_id}`/`{dataset_id}` 패턴과 달리 link 는 고유 id 가 없음).
- LTM D-17/repository.py: `create_link(conn, *, model_id, dataset_id)` 이미 구현됨(T-009) — 존재하지 않는 model_id/dataset_id 면 `NotFoundError` 발생(AC-5 매핑은 API 라우터 책임), 동일 조합 재삽입 시 복합 PK 제약으로 `sqlite3.IntegrityError` 그대로 전파(흡수하지 않음, 중복 정책 미정). `list_links(conn)` 도 구현됨(AC-4), `[{model_id,dataset_id}, ...]` 반환.
- 패턴 재사용(LTM §2): 업로드 라우터 6단계 구조는 이 Task 와 무관(파일 업로드 아님). 대신 models.py/datasets.py 의 "422+ERROR 로그로 계약 위반 처리" 스타일을 재사용 — `NotFoundError`→404(또는 422, AC-5 는 "4xx"로만 명시), `IntegrityError`→409 로 매핑 권장(링크 중복은 "충돌"에 해당). ruff B008(Depends 기본값) 오탐은 인라인 `# noqa: B008` 로 억제(I-15, 아직 전역 ignore 미결정).
- backend charter: `app/api/`, `app/eval/` 소유. `app/api/__init__.py` 에 라우터 등록 패턴(FastAPI `app` 인스턴스 + `include_router`, D-19) 그대로 재사용.

## 4. 발견 사항 (LTM 후보)
- 결정: `POST /links` 응답 바디는 `{model_id, dataset_id}` (link_id 없음 — model_dataset_link 는 복합 PK 뿐, FR-001.md "또는 동등 응답"에 해당). `sqlite3.IntegrityError`(동일 (model_id,dataset_id) 재삽입) → HTTP 409 로 매핑(기술적 충돌 표현일 뿐, "중복 연결을 영구히 금지한다"는 비즈니스 정책 확정은 아님 — 아래 Task 후보 참고).
- 패턴: 라우터 3종(`models.py`/`datasets.py`/`links.py`) 모두 동일한 `get_db` 의존성 + `app.dependency_overrides` 테스트 격리 패턴을 공유 — 추후 `runs.py`(T-015)도 동일 패턴 재사용 가능.
- 이슈/리스크: 동일 (model_id, dataset_id) 조합의 "중복 연결" 허용 여부는 FR-001.md Out of scope 로 여전히 미결정(기존 I-02 는 model/dataset 재업로드 정책이라 별개 이슈) — 현재 구현은 DB 제약을 그대로 409 로 번역하는 보수적 선택.
- 교훈: Repository 계층(T-009)이 이미 `create_link`/`list_links` 를 구현해 둔 덕분에 이번 Task 는 순수하게 FastAPI 라우터 계층 + 에러 매핑 + 테스트에만 집중할 수 있었음 — 계층 분리(프레임워크 독립 도메인 로직)가 실제로 작업 속도를 높인 사례.
