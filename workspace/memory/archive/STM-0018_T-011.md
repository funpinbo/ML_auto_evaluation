## 4. 발견 사항 (LTM 후보)
- 결정: `GET /models`/`GET /datasets` 는 T-040/D-21/D-22 계약을 그대로 구현(변경 없음) —
  응답 바디가 architecture 문서의 예시와 1:1 일치함을 테스트로 확인.
- 패턴: 업로드 라우터(`app/api/models.py`, `app/api/datasets.py`)는 "① 저장 디렉토리
  모듈 속성(테스트가 monkeypatch) → ② `_safe_storage_name()` 으로 저장 → ③ 경로 이탈
  가드 → ④ 도메인 계약 검증(계약 위반 시 4xx+ERROR 로그, 파일/DB 레코드는 그대로/미생성)
  → ⑤ `repo.create_*` 호출 → ⑥ INFO 로그" 순서의 동일한 구조를 따른다. 이후 유사 업로드
  엔드포인트가 생기면 같은 틀을 재사용할 수 있다.
- 이슈/리스크: `_safe_storage_name()` 이 `models.py`/`datasets.py` 에 완전히 동일한 코드로
  중복되어 있다(의도적 — 지시사항에 따라 "동일한 패턴 재사용", 공유 모듈 추출은 범위 밖으로
  명시됨). 세 번째 업로드 엔드포인트가 생기면 공유 유틸(예: `app/eval/storage.py` 또는
  `app/api/_upload_utils.py`)로 추출하는 리팩토링이 필요해질 수 있음 — architecture 판단
  필요(§5 에 Task 후보로 남김).
- 교훈: CSV 컨벤션 검증은 pandas 없이 표준 `csv` 모듈로 헤더 열 수만 보면 충분하다 —
  팀 표준(02§1, charter) "런타임 의존성 최소화"에 맞춰 평가 엔진/API 코드 경로에는 pandas를
  끌어들이지 않음(pandas 는 fixtures/ 사용자 스크립트 내부에서만 쓰임, requirements.txt 주석 참조).
