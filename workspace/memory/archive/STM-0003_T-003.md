## 4. 발견 사항 (LTM 후보)
- 결정: `app/eval/repository.py` 의 `SCHEMA_DDL`/`init_schema()` 를 30§5.1 ERD 확정 DDL 로 채택 — 5테이블(model/dataset/model_dataset_link/run/evaluation), enum 4종(framework/problem_type/problem_type_source/metric/status는 problem_type_source 포함 5개 CHECK), `CREATE TABLE IF NOT EXISTS`(앱 시작마다 호출해도 안전), 인덱스 3개(`idx_evaluation_run_status`, `idx_evaluation_model`, `idx_model_dataset_link_dataset`)
- 결정: 동시성 최적화(WAL 등)는 도입하지 않음 — NFR-004(동시 사용자 1명) 전제, charter §10 과설계 금지 지침 따름
- 패턴: schema_validation.py 의 합성 fixture 검증 방식을 그대로 재사용해 실제 repository.py DDL(SCHEMA_DDL)을 in-memory sqlite 에서 재검증 — CHECK/FK/복합 PK 제약과 KPI-02 집계 쿼리의 인덱스 사용(EXPLAIN QUERY PLAN)까지 확인하는 패턴은 향후 스키마 변경 시 그대로 재사용 가능
- 이슈/리스크: (model, dataset) 재업로드 시 신규 레코드 vs 갱신 정책은 30§2/LTM I-02 대로 여전히 **미정** — 이번 DDL 은 이를 확정하지 않음(model_dataset_link 복합 PK 는 동일 링크 중복만 막을 뿐, model/dataset 자체 재업로드 정책과는 무관). repository.py 상단 주석에도 이 미정 상태를 명시해 T-009(backend 쿼리 구현) 담당자가 놓치지 않도록 함
- 교훈: dba 소유(DDL)와 backend 소유(쿼리 함수) 경계를 파일 내 주석 섹션으로 명시해두면, 동일 파일을 공유하는 다음 Task(T-009) 담당자가 수정 범위를 헷갈리지 않음

## 5. 새로 발견된 Task (Task 후보)
- [architecture] tasks.md T-009 가 "[dba] Repository 모듈 구현(쿼리 함수)"로 표기돼 있으나, dba charter §2 "하지 않음"은 애플리케이션 쿼리 구현을 backend 소유로 명시하고 있어 담당 팀 표기가 charter 와 어긋남 — T-009 실행 전 담당 팀을 backend 로 재확인/정정 필요(또는 charter 를 재확인해 의도적 예외인지 명시)
- [backend] T-009 에서 (model, dataset) 재업로드 시 신규 vs 갱신 정책(30§2/LTM I-02, 미정)을 확정하고 쿼리 함수에 반영 필요 — dba 는 스키마 레벨에서 이를 강제하지 않음(복합 PK 는 중복 링크만 방지)
- [backend] (architecture 리뷰 발견, T-003 검증) `app/eval/repository.py` 의 `SCHEMA_DDL` 은 FK(`REFERENCES`)를 선언하지만 SQLite 는 연결마다 `PRAGMA foreign_keys = ON` 을 실행해야 FK 제약이 실제로 강제된다 — dba 의 scratchpad 검증 스크립트는 이 PRAGMA 를 수동으로 켠 상태에서만 FK 거부를 확인했고, `init_schema()`/운영 코드 어디에도 이 PRAGMA 를 설정하는 부분이 없다. T-009(Repository 쿼리 함수) 또는 커넥션 팩토리 구현 시 커넥션을 열 때마다 `PRAGMA foreign_keys = ON` 을 실행하도록 반영 필요 — 그렇지 않으면 FK 제약이 조용히 무력화되어(R1 류와 유사한 잘못된 상태 리스크) `run_id`/`model_id`/`dataset_id` 참조 무결성이 실제로는 지켜지지 않음
